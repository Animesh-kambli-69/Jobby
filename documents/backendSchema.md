# Jobby — Backend Schema Document


Jobby stores its data in a MongoDB database (`jobgraph` by default) using Mongoose. The current backend has five collections: `users`, `jobs`, `applications`, `interviewanalyses`, and `interviewrecordings`. Interview videos are stored in Cloudinary, with only their URLs and related metadata saved in MongoDB.

This document describes the current schema, its limitations, and the proposed v1.0 changes.

---

# 1. Entity Relationships

## 1.1 Current Relationships

The current database contains five collections and uses Cloudinary for interview video storage.

- One recruiter owns many jobs.
- One job has many applications.
- One candidate has many applications, interview analyses, and interview recordings.

Two relationships need improvement:

1. Applications identify candidates through an email string instead of a direct user reference.
2. `jobs.recruiterId` exists but is not populated by the current job-creation flow, so job ownership falls back to matching company names.

The v1.0 schema replaces these weak relationships with ObjectId references.

## 1.2 Collection Reference

The current field definitions reflect the uploaded `backend/models/*.js` files. Every document also contains MongoDB's `_id` (`ObjectId`) and Mongoose's `__v` version field.

**Current limitation:** Question text, interview session ID, interview type, and difficulty are missing. Consequently, individual answers cannot be grouped into a complete interview.

# 3. Indexes, Constraints, and Integrity Rules

## 3.1 Current Indexes

`config/db.js` calls `Model.init()` for `User`, `Job`, and `Application` during startup. These models build their indexes at boot. `InterviewAnalysis` and `InterviewRecording` indexes are built lazily on first use.

| Collection | Index | Type / Purpose |
|---|---|---|
| `users` | `{ email: 1 }` | Unique; login lookup and duplicate-account prevention |
| `applications` | `{ jobId: 1, candidateEmail: 1 }` | Unique; one application per candidate per job |
| `interviewanalyses` | `{ userId: 1 }` | Single-field index for per-user history |
| `interviewrecordings` | `{ userId: 1 }` | Lists and filters |
| `interviewrecordings` | `{ interviewType: 1 }` | Lists and filters |
| `interviewrecordings` | `{ cloudinaryPublicId: 1 }` | Recording lookup |

Before creating the unique applications index, `deduplicateApplications()` groups records by `jobId` and lowercased email, keeps the oldest document, and deletes duplicates.

## 3.2 Indexes Required for v1.0

| Collection | Proposed index | Purpose |
|---|---|---|
| `users` | `{ role: 1, resumeScore: -1 }` | Candidate pool sorted by score |
| `users` | `{ role: 1, skillsNormalized: 1 }` | Filtering by canonical skills; multikey index |
| `jobs` | `{ status: 1, createdAt: -1 }` | Listing active jobs |
| `jobs` | `{ recruiterId: 1, status: 1 }` | Recruiter-owned postings and summaries |
| `jobs` | Text index on `title`, `requiredSkills`, `company`, and `description` | Keyword search |
| `applications` | `{ candidateId: 1, appliedAt: -1 }` | Candidate application history |
| `applications` | `{ jobId: 1, matchScore: -1 }` | Ranking applicants for a job |
| `applications` | Unique `{ jobId: 1, candidateId: 1 }` | Replaces email-based uniqueness |
| `interviewsessions` | `{ userId: 1, createdAt: -1 }` | Interview history |
| `passwordresets` | `{ expiresAt: 1 }` with TTL 0 seconds | Automatically delete expired tokens |

The job text index uses weights of 10 for `title`, 5 for `requiredSkills`, 3 for `company`, and 1 for `description`.

## 3.3 Integrity Rules

| Rule | Current enforcement | v1.0 enforcement |
|---|---|---|
| Email unique per user | Unique index | Unique index plus lowercase and trim at schema level |
| One application per candidate per job | Unique index on `jobId` and email | Unique index on `jobId` and `candidateId` |
| Only active jobs accept applications | Not enforced | Controller check returning HTTP 400 with `JOB_CLOSED` |
| Applicant is the logged-in candidate | Request-body fields are trusted | Server fills candidate identity from `req.userId` |
| Recruiter owns the job | `recruiterId` match or company-name match | `recruiterId` only |
| Application status transitions | Accepted/rejected can be set at any time | `pending` → `reviewed` → `accepted` or `rejected`; terminal states are locked |
| Scores remain in range | Mongoose min/max on resume and interview-analysis fields | Same checks, plus `matchScore` min 0 and max 100 |
| Deleting a user | No cascade | Applications anonymised; analyses deleted; recordings deleted from MongoDB and Cloudinary |
| Closing a job | No route currently exists | Close job without deleting it; applications are retained |

## 3.4 Document Size Watch-list

| Field | Typical size | Risk | Proposed action |
|---|---|---|---|
| `users.resumeFileData` | Up to 5 MB | Slow reads, MongoDB's 16 MB document limit, memory spikes | Move file bytes to object storage |
| `users.resume` | 5–50 KB | Sent in `/me` responses | Exclude from default projections |
| `users.skillsEmbedding`, `jobs.skillsEmbedding` | Approximately 6–12 KB | Unnecessary bandwidth in list responses | Remove after matcher rewrite or move to a vector index |
| `applications.resume` | 5–50 KB per application | Duplicates resume data for each job application | Store a reference to the profile version instead |

# 4. Target v1.0 Schema Changes

The v1.0 design retains the five existing collections and adds three new collections:

- `interviewsessions`
- `passwordresets`
- `auditlogs`

All schemas will enable `timestamps: true`. Email-based application joins will be replaced by ObjectId references.

## 4.1 Change Summary

### Users

**Add:**
- `skillsNormalized`: array of canonical skill names.
- `resumeFile`: object containing `key`, `url`, `name`, `mimeType`, `size`, `uploadedAt`, and source.
- `emailVerified`: Boolean.
- `status`: `active` or `suspended`.
- `shareRecordings`: Boolean.
- `lastLoginAt`: Date.
- `deletedAt`: Date.
- `admin` as an additional role.

**Change:**
- Normalise email using lowercase and trim.
- Enable timestamps.

**Remove:**
- `resumeFileData`.
- Duplicate `resumeFileName` and `resumeFileMimeType`.
- Unused Cloudinary resume fields.
- `skillsEmbedding`.

### Jobs

**Add:**
- `skillsNormalized`.
- `employmentType`: `full-time`, `part-time`, `contract`, or `internship`.
- `experienceLevel`: `entry`, `mid`, or `senior`.
- `salaryMin`.
- `salaryMax`.
- `currency`.
- `closedAt`.

**Change:**
- Make `recruiterId` required.
- Derive the company from the recruiter.

**Remove:**
- `skillsEmbedding`.

### Applications

**Add:**
- `candidateId`, required.
- `matchedSkills`.
- `missingSkills`.
- `statusHistory`, containing status, timestamp, and actor.
- `reviewedAt`.

**Change:**
- Add `withdrawn` to the status enum.

**Remove:**
- `candidateName`.
- Resume snapshot; retrieve resume information from the user's profile instead.

### Interview Analyses

**Add:**
- `sessionId`.
- `questionIndex`.
- `question`.

### Interview Recordings

**Add:**
- `sessionId`.
- `deleteAfter` for retention.

### New Collections

**`interviewsessions`:** Stores interview-level information, including questions, status, scores, feedback, duration, and consent.

**`passwordresets`:** Stores `userId`, `tokenHash`, `expiresAt`, and `usedAt`.

**`auditlogs`:** Stores `actorId`, `action`, `entity`, `entityId`, `meta`, and `createdAt`.

# 5. Migration Plan, Seed Data, Retention, and Backup

## 5.1 Migration Steps

Migrations should be implemented as idempotent scripts in `backend/scripts/migrations/` using `migrate-mongo`. Run every migration on staging first, with a fresh backup.

1. **M001 — Normalise emails:** Lowercase and trim `users.email`. Report collisions between accounts that differ only by case and manually merge them before recreating the unique index.

2. **M002 — Backfill `candidateId`:** Find users using lowercased `candidateEmail`. Log orphaned applications without a matching user and retain them with `candidateId: null`, flagged for review.

3. **M003 — Replace the unique index:** Create the unique `{ jobId, candidateId }` index, then drop `{ jobId, candidateEmail }`.

4. **M004 — Backfill `recruiterId`:** For jobs without a recruiter reference, assign the single recruiter whose company matches. If there are zero or multiple matches, assign the job to an admin and list it for follow-up.

5. **M005 — Move resume files:** Stream `users.resumeFileData` to private object storage. Write `resumeFile.key`, `url`, `name`, `mimeType`, and `size`, then unset the Buffer and duplicate fields. Process 100 users per batch.

6. **M006 — Canonicalise skills:** Compute `skillsNormalized` for users and jobs using the alias map. Recalculate `matchScore`, `matchedSkills`, and `missingSkills` for open applications.

7. **M007 — Remove embeddings:** Unset `skillsEmbedding` on users and jobs once the new matching system is live.

8. **M008 — Initialise status history:** Create an initial `statusHistory` entry using `{ status, at: appliedAt }` for each application.

9. **M009 — Build indexes:** Create the new indexes listed in Section 3.2 in the background on Atlas.

### Rollback

Every migration step before M007 is additive. If a step fails validation, restore from the pre-migration snapshot.

## 5.2 Seed Data

The current `npm run seed` command (`backend/seed.js`) wipes users, jobs, and applications before inserting development data.

| Entity | Count | Examples |
|---|---:|---|
| Candidates | 5 | `alice@example.com`, `bob@example.com`, `carol@example.com`, `david@example.com`, `emma@example.com` |

### v1.0 Seed Changes

- Refuse to run when `NODE_ENV=production`.
- Set `recruiterId` on jobs.
- Add one admin account.
- Include sample applications in every status.
- Add two completed interview sessions so every screen has development data.

## 5.3 Data Retention

| Data | Retention | Mechanism |
|---|---|---|
| Interview recordings | Proposed 90 days or until user deletion | `deleteAfter` and a daily job that deletes files from Cloudinary and MongoDB |
| Interview analyses and sessions | Until account deletion | Cascade on deletion |
| Password reset tokens | 30 minutes | TTL index on `expiresAt` |
| Closed jobs and applications | 24 months, then archive | Scheduled job |
| Deleted accounts | Personal fields removed within 30 days; applications anonymised | `deletedAt` and purge job |
| Audit logs | 12 months | TTL index |

## 5.4 Backup and Recovery

| Item | Target |
|---|---|
| Backups | MongoDB Atlas continuous backup with point-in-time restore; daily snapshots retained for 7 days and weekly snapshots for 4 weeks |
| RPO / RTO | Recovery point objective: no more than 1 hour; recovery time objective: no more than 4 hours |
| Restore drill | Quarterly restore to staging, verified using the smoke test |
| Media | Cloudinary assets are not covered by Atlas backups; enable Cloudinary backup or accept re-recording as the recovery path |

# 6. Implementation Priorities

The v1.0 backend work should prioritise data integrity, reliable ownership checks, interview history, and safe file storage.

1. Normalise email addresses and enforce consistent account uniqueness.
2. Replace email-based application joins with `candidateId` ObjectId references.
3. Populate and require `recruiterId` for every job.
4. Add interview sessions so individual answers can be grouped into complete interviews.
5. Move resume file bytes out of MongoDB documents.
6. Add canonical skill fields and consistent matching data.
7. Enforce application eligibility and status-transition rules on the server.
8. Add the required indexes and protect production from destructive seed operations.
9. Implement retention jobs, account-deletion handling, and backup procedures.
10. Run migrations on staging, validate the results, and verify rollback and recovery procedures.

The goal is to move Jobby from a working prototype schema to a more reliable v1.0 data model with clear relationships, consistent matching, traceable application decisions, and manageable data-retention rules.
